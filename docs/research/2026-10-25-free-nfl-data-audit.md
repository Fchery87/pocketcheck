# Free NFL data feasibility audit

Research date: 2026-10-25. Scope: a personal, locally run NFL pregame research application covering full-game moneyline, spread, and total. This is a source audit and implementation proposal, not a claim that an ingestion pipeline has been built or that a prediction model has an edge.

## Feasibility conclusion

A useful research workflow can target $0 in additional fixed data costs: public NFL datasets, user-entered sportsbook quotes, official injury reports, public weather forecasts, and manual supplementation. Existing AI access is a separate user-supplied resource; possessing an API key does not establish prepaid or free API usage.

The audit does **not** establish a complete free archive of the user's sportsbook prices, injury information, and forecasts as they appeared at arbitrary past decision times. Prospective capture must begin with the first analysis. Historical statistical testing and validation of the complete live research workflow are different deliverables.

Evidence classifications below:

- **Sampled:** inspected an actual payload or source page, with the exact limitation stated.
- **Documented:** verified owner documentation or loader source; current payload not successfully inspected.
- **Unverified:** coverage, freshness, licensing, or point-in-time behavior remains unresolved.

### Injury availability: resolve the apparent contradiction

Maintainer-linked [2025 issue reports](https://github.com/nflverse/nflreadpy/issues/17) documented missing injury data. However, the later [nflreadr change](https://github.com/nflverse/nflreadr/commit/23f915a) replaces the old outage warning with the daily-update description. It would be incorrect to present the old warning as proof that the outage persists today.

It would also be incorrect to declare the feed healthy from documentation alone. The current release attachment bodies were not inspected in this audit. Treat current-season automated injury coverage as **unverified** until an implementation-time sample establishes season, week, teams, source/report dates, and expected rows. Never silently substitute 2024 reports for a 2026 analysis.

## Update and schema details that matter

The [nflverse schedule](https://nflreadr.nflverse.com/articles/nflverse_data_schedule.html) describes frequent schedule refreshes, game-day/nightly play-by-play and team-stat updates, later corrections, and timestamped depth-chart updates from 2025. It also says FTN participation data for 2023 onward arrives after the postseason, making that release unsuitable as a live in-season input. These are expected schedules, not service guarantees.

The [schedule dictionary](https://raw.githubusercontent.com/nflverse/nflreadr/main/data-raw/dictionary_schedules.csv) needs special attention: positive `spread_line` means the home team is favored. This differs from displaying a selected favorite as −3.5. Convert explicitly and test the sign convention. The dictionary describes kickoff times in Eastern time, so convert using the date-aware `America/New_York` zone rather than a fixed UTC offset.

Odds columns include moneylines, spread prices, and total prices, but their presence does not establish full coverage or the book and observation time behind each value. A row-level betting study must first profile null rates and source provenance. Do not label such fields as the user's available price or assume they support opening-to-closing movement analysis.

The file also includes weather, starting quarterback, scores, and roof-related fields. Their presence in a completed-game record does not prove they were available before the intended prediction cutoff. Exclude any field without a defensible pregame availability rule from retrospective features.

## Weather acquisition and historical leakage

The [NWS documentation](https://www.weather.gov/documentation/services-web-api) describes `/points/{latitude},{longitude}` returning linked forecast endpoints. Resolve the point, select the period containing kickoff, and save both the issue/update metadata and period times. Recheck point mappings periodically. An outdoor forecast should not become an assumed on-field condition for a closed roof.

**Proposed design:** store forecast snapshots prospectively. A historical record of actual game-day wind can support a descriptive study, but cannot recreate a forecast known on Tuesday. If a retrospective forecast archive is not verified, omit weather from that backtest and state why. For international games outside verified coverage, require a separately audited forecast source or manual evidence; do not quietly substitute the nearest US forecast.

## Reuse and operating limits

The [nflverse organization licensing statement](https://github.com/nflverse) distinguishes most releases under CC BY 4.0 from FTN data under CC BY-SA 4.0 and directs users to dataset-specific notices. Preserve attribution and dataset-specific terms in source metadata. Start with non-FTN inputs; do not treat all freely downloadable data as having identical reuse conditions. No team logos or paid proprietary grades are required for the first release.

**Proposed zero-additional-cost operating policy:**

- Run collection only on user action and reuse cached downloads until the relevant source refresh window.
- Store large raw statistical files on the user's computer; put compact feature snapshots, citations, report versions, and journal entries in Neon.
- Recheck Neon allowances during setup; do not assume unlimited storage, compute, retention, or permanent free-plan terms.
- Keep AI requests explicit and bounded by tokens/time/retries. Respect the user's existing allowance; do not automatically buy credits or fall back to another billable provider.
- Treat free search, news discovery, and model inference as separate capabilities. A text-model endpoint does not establish free web search or automatic access to fresh reports.
- Prefer allowlisted public sources and user-supplied links. A research assistant's browsing tool is not a production capability of the app.
- Do not bypass access controls, defeat blocking, or build a critical path around an undocumented ESPN endpoint. If a source fails or its reuse conditions are unresolved, request manual evidence or mark the input missing.

## Minimum viable evidence packet

This is a proposed implementation contract, not a verified source capability. For each analysis, persist:

1. Canonical event identity, scheduled kickoff, season/type/week, venue and home/away assignment.
2. Selected market, selected side, exact line/price, sportsbook, settlement-rule notes, quote observation time, and opposing price if supplied.
3. A snapshot of lagged team features: source files, hashes/versions, calculation definitions, games included, and cutoff time.
4. Relevant quarterback and other player availability facts with source URLs, dated updates, retrieval times, and unresolved conflicts.
5. A kickoff-period forecast snapshot where applicable, or a visible reason weather is absent or irrelevant.
6. Concise cited context, counterevidence, assumptions, missing inputs, calculation version, model artifact version, and AI provider/model/prompt version.
7. Immutable report versions and separately recorded actual wagers/results.

Use separate timestamps for `published_at` when actually known, `retrieved_at`, and `observed_at` for user-reported facts. Never invent a publication timestamp from the retrieval time. A mutable webpage with an old publication date may contain newer information.

## Validation boundaries

**Historical statistical testing:** can test an explicitly limited feature set assembled from earlier completed games. Where historic versions are absent, disclose use of corrected data and possible preprocessing-model contamination. Use chronological splits and keep all records from one game together. Do not ask today's AI to research an old matchup and call its answer a pregame prediction: its knowledge and retrieved pages may contain the result.

**Prospective workflow validation:** record the thesis, prices, evidence, and calculation/model versions before kickoff. Later outcomes must be linked without rewriting the original report. Track all completed analyses, including passes; distinguish them from actual bets. This is the practical route for testing injury/news/weather context when historic evidence versions are incomplete.

**Market comparison:** only compare prices for the same outcome, line, settlement terms, and appropriate time. If the user's final pregame quote is manually captured, label it that way; it is not necessarily the market-wide closing price. If no comparison exists, leave closing-line value unavailable.

## Implementation-time source acceptance checklist

These are unresolved checks to execute before enabling automatic collection. They are not requests for another product interview.

- Fetch current schedule and completed-game samples; measure schema, season/type coverage, freshness, and missing betting columns.
- Fetch one historical and one current play-by-play/team-stat file; verify identifiers, numeric types, calculation denominators, and file size.
- Fetch current injury data; compare a sample against an official dated team report. Reject missing or stale season/week data.
- Establish permitted article retrieval for each chosen source; retain a manual path when unavailable.
- Resolve one stadium through NWS and inspect a kickoff-hour payload, issued time, units, nulls, and response-cache headers.
- Test explicit missing-source behavior: show the gap, keep prior snapshots intact, and return conditional analysis or a pass when the missing input is material.
- Verify the selected AI account's callable model list and allowance without assuming advertised provider capabilities work for that account.

The audit supports a staged research application. It does not support claims of comprehensive free real-time coverage, fully reconstructed historical news states, independently verified executable sportsbook prices, or proven profitability.
